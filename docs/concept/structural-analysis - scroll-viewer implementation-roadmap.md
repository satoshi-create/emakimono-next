# 絵巻物ビューアー（Emakimono Viewer）イノベーション構造分析レポート 実装ロードマップ版

## 0. この文書の位置づけ
本ドキュメントは `structural-analysis - scroll-viewer v2.md` を実装計画へ落とし込んだ版である。目的は、ローエンド市場への浸透を最優先しつつ、既存の SEO 資産とビューア資産を壊さずに段階アップデートするための順序を明確にすることにある。

前提として、現行コードベースには以下の資産がすでに存在する。

- `EmakiConteiner.js` による横スクロール、初回自動再生ナッジ、再生モード、ハッシュ付きシーン遷移
- `Meta.js` による canonical / hreflang
- `buildEmakiJsonLd.js` による `VisualArtwork` JSON-LD
- `next-i18next` による `ja` / `en` の多言語配信
- `next-pwa`、Cloudinary、`next/image` を軸にした配信基盤

したがって、戦略は「ゼロから作り直す」ではなく、「ローエンド施策で市場を開きながら、裏側を安全に更新する」が基本方針となる。

---

## 1. ロードマップの基本原則

### 1.1 優先順位
1. まずローエンド向けの入口体験を改善する
2. 次にその改善を支える最低限のリファクタリングを行う
3. その後、Next.js を段階的に更新する
4. 最後にハイエンド機能と再利用エコシステムへ広げる

### 1.2 やらないこと
- ローエンド UI 改修と Next.js メジャーアップデートを同時にやらない
- App Router 移行をアップグレードの前提にしない
- SEO、URL、既存共有導線を壊す全面再構築をしない

### 1.3 成功条件
- 初見ユーザーが説明なしでも「右から左へ流れる物語」として理解できる
- 共有・再訪・多言語導線が維持または改善される
- 主要 URL、canonical、hreflang、JSON-LD が維持される
- 既存コードの技術的負債を、ユーザー価値を止めずに圧縮できる

## 3. Phase 0: 計測と安全装置の整備

### 目的
ローエンド施策が本当に効いているかを判定できる状態を作る。実装の順序を誤らないためのベースラインを整える。

### 実施項目
- 現行の主要イベントを棚卸しする
  - `trackAutoScrollStarted`
  - `trackAutoScrollInterrupted`
  - `trackManualScroll`
  - `sns_share_click`
  - `scene_modal_open`
- 主要画面の確認手順を文書化する
  - `/[slug]` 表示
  - `#scene` ハッシュ付き URL
  - フルスクリーン切替
  - locale 切替
  - 共有導線
- ベースライン指標を決める
  - 初回自動再生開始率
  - 自動再生中断率
  - シェアボタン利用率
  - 直帰しやすい絵巻ページ
  - 言語別アクセス比率

### 完了条件
- 変更前後を比較できる指標が揃う
- リリース後に見るべき KPI が定義される

## 4. Phase 1: ローエンド導入体験の確立

### 目的
「知らない人でもすぐ見られる」状態を最優先で作る。ここが本ロードマップの中核である。

### 実装テーマ

#### 4.1 自動再生の再定義
現行コードには初回訪問時の自動スクロールと、再生モードがすでにある。これをローエンド戦略の中心機能として再定義する。

- 初回ナッジを「右から左へ流れることを身体で理解させる UI」として扱う
- 必要に応じて初期値をより明確にする
  - 初回のみ自動再生
  - 一定条件では常時再生寄りに寄せる
  - `prefers-reduced-motion` 配慮
- ハッシュ付き URL の自動再生スキップは維持する

#### 4.2 YouTube 的 UI シェル
「完コピ」ではなく、メンタルモデルの借用として実装する。

- 下部固定のコントロール群へ整理
- 再生 / 停止の主導線を明確化
- シーン位置を示す進捗 UI を視覚的に強化
- ヘルプ依存を減らし、見れば分かる UI に寄せる

#### 4.3 ローエンド向け短文説明
長文を増やすのではなく、短く要点だけ伝える。

- 「これは右から左へ流れる物語です」
- 「止めて拡大し、気になる場面を共有できます」
- 「詳細を読みたい人だけ追加解説に進める」

### 対象ファイルの中心
- `src/components/emaki/layout/EmakiConteiner.js`
- `src/components/emaki/navigation/EmakiNavigation.js`
- `src/components/emaki/viewer/PositionIndicator.js`
- `public/locales/ja/common.json`
- `public/locales/en/common.json`

### 完了条件
- 初見ユーザーがヘルプを読まなくても操作意図を把握できる
- 自動再生が「作法の説明」ではなく「体験の入口」として機能する

## 5. Phase 2: 共有と回遊の強化

### 目的
ローエンド体験を一回の閲覧で終わらせず、共有と再訪を増やす。

### 実装テーマ

#### 5.1 シーン共有の磨き込み
現行の `ShareButtons.js` は URL 共有が中心で、ここはすでに資産がある。

- シーン URL コピーを主導線にする
- 共有文言をローエンド向けに調整する
- モバイルの Web Share 体験を優先する

#### 5.2 ハッシュ起点の回遊強化
- `#scene` で開いたときの閲覧継続率を上げる
- 特定シーンから入っても全体へ戻れる導線を改善する

#### 5.3 ガイドと説明の役割整理
- 詳しいヘルプは残す
- ただし、主要導線はヘルプの外に出す
- `/guide` は補助、ビューア内 UI は主導線と位置づける

### 完了条件
- シェア利用率が上がる
- ハッシュ付き流入後の閲覧継続が改善する

---

## 6. Phase 2.5: 小規模リファクタリング

### 目的
Next.js 更新前に、変更しやすい最小単位へ分ける。全面再設計ではなく、「次の変更を安全にするための分割」に限定する。

### 対象
- `EmakiConteiner.js` の責務分割
  - 自動再生
  - 再生モード
  - シーン検出
  - UI 表示状態
- `_app.js` のうち viewer に強く依存する状態管理の整理

### 方針
- Hook 抽出を優先する
  - `useAutoScroll`
  - `usePlayMode`
  - `useSceneDetection`
- 見た目変更と責務分離を同時にやりすぎない

### 完了条件
- Next.js 更新時に触るファイルの責務が明確になる
- ビューアの挙動差分を追いやすくなる

---

## 7. Phase 3: Next.js 基盤アップデート

### 目的
SEO と URL を壊さず、Next.js 12 の EOL リスクを下げる。

### 基本方針
- Pages Router を維持する
- App Router へは移行しない
- 機能追加を止めた短期スプリントとして実施する

### 主な論点

#### 7.1 依存関係整理
- `next` を 15.x または 16.x へ
- `react` / `react-dom` の追従
- `eslint-config-next` の追従
- 未使用・古い依存の整理

#### 7.2 画像と配信
- `next/image` 周辺の破壊的変更への対応
- Cloudinary 前提の配信を維持
- LCP とスクロール中読み込みへの影響確認

#### 7.3 PWA
- `next-pwa` の継続可否確認
- 必要なら別ライブラリへの移行

#### 7.4 i18n
- `next-i18next` + Pages Router を当面維持
- locale ルーティング、`hreflang`、`canonical` を回帰確認

### 必須回帰テスト
- `ja` / `en` 各ページ表示
- `Meta.js` の canonical / hreflang
- `VisualArtwork` JSON-LD
- `#scene` 共有 URL
- 初回自動再生
- 再生 / 停止
- fullscreen 切替
- PWA 基本動作

### 完了条件
- 本番 SEO シグナルを壊さずに最新サポート系へ移行できる
- ローエンド導線の挙動が維持される

## 8. Phase 4: 体験拡張

### 目的
入口改善後に、滞在価値と使い方の幅を広げる。

### 実装テーマ

#### 8.1 ズーム
- まずは停止中限定の段階ズームから始める
- ピンチズームは後回しでもよい

#### 8.2 遷移とアニメーション
- ページ遷移のフェード
- UI のやわらかい出入り
- ただし、主役は絵巻であり、演出過多にしない

#### 8.3 Ambient / Background 利用
- フルスクリーン + UI 自動非表示 + ループ再生
- 「環境背景として流す」使い方の提案

### 完了条件
- ローエンド導線を損なわずに滞在時間と再訪機会を伸ばせる

## 11. 実装順の論理
このロードマップの重要点は、「ローエンド戦略」と「段階アップデート」を対立させないことである。

- ローエンド戦略は、市場への入り口を広げる
- 段階アップデートは、その入口を壊さずに運用を持続可能にする

したがって実装順は、

1. 入口を作る
2. 入口を支えるコードを軽く整える
3. 土台を更新する
4. その上で広げる

という順序になる。

これは単なる開発都合ではなく、クリステンセン理論でいう「非消費の開拓」を優先しながら、既存の価値ネットワークの上流資産を壊さないための順番でもある。

## 12. リスクと回避策

| リスク | 起きやすい場面 | 回避策 |
|---|---|---|
| UI 改修が複雑化する | Phase 1 | まずは自動再生と再生 UI に絞る |
| 既存 SEO が落ちる | Phase 3 | canonical / hreflang / JSON-LD を固定観察する |
| ビューア回帰バグ | Phase 2.5 / 3 | ハッシュ、fullscreen、再生を最優先で回帰確認する |
| 実装がハイエンドへ逸れる | Phase 4 以降 | ローエンド指標を先に達成条件に置く |
| App Router 移行欲求でスコープが膨らむ | Phase 3 | Pages Router 維持を明文化する |

## 14. 結論
Emakimono Viewer の実装ロードマップは、ローエンド戦略を先に進め、その価値が立ち上がったあとで基盤を段階的に更新する形が最も合理的である。

最初にやるべきことは、最先端技術の導入でも全面刷新でもない。最初にやるべきことは、「初見ユーザーが右から左へ流れる絵巻を、動画のように自然に理解できる入口」を作ることだ。

その入口が立ち上がれば、Next.js 更新、PWA 更新、IIIF 連携、AI 活用は後から安全に積み上げられる。つまり本プロジェクトの実装戦略は、

> ローエンドで市場を開き、段階アップデートで壊さず伸ばす

という一文に要約できる。
